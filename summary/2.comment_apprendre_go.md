# Comment apprendre Go ?

Apprendre Go, quand on vient d'un autre langage, passe par l'apprentissage de la syntaxe, cela va de soi. Mais cela passe surtout par la pratique des notions fondamentales du langage, une par une, avant de s'attaquer à des sujets plus larges comme le backend ou le cloud natif.

## Les notions à maîtriser

Ce repo est organisé pour couvrir ces notions, chacune dans son propre package sous `internal/`, avec des exercices associés sous `exerices/` :

- **variables** : déclaration (explicite, inférée, courte), valeurs zéro, conversion de type, portée, déclaration multiple, pointeurs
- **constantes** : constantes simples, blocs de constantes, l'identifiant `iota`
- **shadowing** : le piège du masquage de variable, en particulier avec `:=` et les erreurs
- **flow** (structures de contrôle) : if/else, switch, type switch, boucles for, range, labels
- **learn_functions** : fonctions, retours multiples, retours nommés, variadique, closures, fonctions anonymes, récursivité, defer
- **types** : types numériques, string/rune/byte, array/slice, map, types nommés, conversions
- **structs_and_pointers** : structs, méthodes (valeur vs pointeur), embedding, comparaison
- **error_handling** : gestion d'erreurs idiomatique, erreurs personnalisées, wrapping, panic/recover
- **interfaces** : interfaces implicites, polymorphisme, type assertion, interface vide, embedding d'interfaces
- **generics** : fonctions et structs génériques, contraintes de type
- **data_structures** : pile, file, liste chaînée, ensemble, matrice 2D
- **tools** : packages standards utiles au quotidien (strings, strconv, time, os)
- **concurrency** : goroutines, channels, select, sync.Mutex/WaitGroup
- **tests** : écrire des tests avec le package `testing`, tests par table, benchmarks

Une fois ces bases posées, viennent les sujets plus larges : la concurrence appliquée à de vrais problèmes, le backend HTTP et gRPC, l'architecture et les tests à l'échelle d'un projet, le cloud natif.

## La méthode

La meilleure façon d'apprendre n'est pas linéaire, notion par notion dans l'ordre du cours. C'est d'écrire un programme, puis de le refactoriser pour le rendre plus court et plus lisible à mesure qu'on découvre de nouvelles notions. On bute sur un concept (une erreur de compilation, un code qui marche mais qui est moche, une répétition qu'on sent évitable), et c'est en cherchant à résoudre ce point de blocage précis qu'on apprend la notion qui manquait.

Les packages `internal/` et les exercices de ce repo ne sont donc pas un programme à suivre dans l'ordre, mais une référence à consulter quand on bute sur quelque chose pendant qu'on écrit son propre code.

### 1. Partir d'un programme, pas d'un chapitre

Écrire quelque chose de concret et d'un peu trop simple au départ (un petit outil en ligne de commande, un calcul, un parseur de texte). Le faire fonctionner, même maladroitement, avant de se soucier de "bien faire".

### 2. Refactoriser activement

Une fois que ça marche, relire son propre code et se demander : qu'est-ce qui est répété, qu'est-ce qui est illisible, qu'est-ce qui pourrait planter. Chercher à le rendre plus court et plus clair, pas juste différent.

### 3. Buter, puis chercher la notion qui débloque

Quand le refactoring révèle un manque (ex: "je répète cette fonction pour int et pour float, il doit y avoir un moyen de factoriser" → generics ; "je n'arrive pas à faire persister un changement dans une boucle" → pointeurs ou slices ; "mon programme plante sans message clair" → error_handling), c'est le bon moment pour aller lire le package correspondant dans `internal/` et faire les exercices ciblés de `exerices/`. La notion se fixe mieux parce qu'elle répond à un problème qu'on a déjà rencontré soi-même.

### 4. Utiliser les outils du langage comme révélateurs de problèmes

- `gofmt -l .` : formatage
- `go vet ./...` : erreurs suspectes détectées statiquement
- `go build ./...` : beaucoup d'erreurs de conception se voient déjà à la compilation
- `go test ./...` et `go test -race ./...` : valider un refactoring sans tout casser, détecter les races conditions sur la partie concurrence

Un message d'erreur du compilateur Go est presque toujours précis et pédagogique : le lire en entier avant de chercher ailleurs. Un échec de test après un refactoring est aussi une information précieuse, pas un échec.

### 5. Recommencer sur un nouveau programme

Une fois le premier programme refactorisé jusqu'à satisfaction, en reprendre un autre, un peu plus ambitieux, qui réutilise les notions déjà acquises et en fait émerger de nouvelles (concurrence, interfaces, tests). Le but n'est pas de couvrir toutes les notions d'un coup, mais de laisser chaque projet révéler les suivantes.
